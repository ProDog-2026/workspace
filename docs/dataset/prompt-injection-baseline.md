# 프롬프트 인젝션 탐지 모델 데이터셋

담당자는 윤주혁이다. 2026-10-18 재구성 기준이며, 학습 데이터, 분리 기준, 가중치, 사용 범위와
실측 결과를 정리했다.

## 설계 방침

정적 탐지기는 최종 악성 판정을 담당하지 않는다.

- 확실한 정상 메일만 `safe`로 통과
- 애매한 메일은 `suspicious`로 동적 분석에 전달
- 강하게 탐지된 메일만 `danger`
- 세 단계는 별도로 학습한 3개 클래스가 아니라 하나의 이진 모델 점수를 두 임계값으로 나눈 구간이다

데이터는 행 단위가 아니라 **공격 계열·시나리오·원본 메일 그룹 단위**로 나눈다. 각 데이터셋마다
그룹을 train 2/3, validation 1/6, test 1/6으로 분할한다. 분할은 `SHA-256(seed:출처:그룹)`
기준이라 실행 순서와 무관하게 같은 결과가 나온다.

### Microsoft LLMail-Inject

- 출처: <https://huggingface.co/datasets/microsoft/llmail-inject-challenge>
- 확인 수준: 데이터셋 카드와 배포 파일을 직접 확인함
- 라이선스: MIT
- 사용 파일: `raw_submissions_phase1.jsonl`, `raw_submissions_phase2.jsonl`,
  `emails_for_fp_tests.json`
- 원본 제출 461,640건 → 제목+본문 완전 중복 제거 후 203,150건
- 그룹: 공격은 `team_id` 304개, 정상은 메일 단위 160개 → 합계 464그룹
- 정상 메일: FP 테스트용 160건

이전 기준 모델이 쓰던 10,000쌍 가공본(`data/processed/llmail-train.jsonl`,
`llmail-external-test.jsonl`)은 더 이상 사용하지 않는다.

**라벨 의미에 주의가 필요하다.** 원본 제출은 전부 공격 *시도*이므로 `prompt_injection=1`로
두었으나, 중복 제거 후 203,150건 중 실제로 exfil 목표를 달성한 것은 약 24,000건(12%)뿐이다.
나머지 88%는 실패한 공격 시도다. 판단을 다시 할 수 있도록 각 행에 `exfil_sent`와 `scenario`를
메타데이터로 보존했다.

### Zenodo Phishing Email Curated Datasets

- 출처: <https://zenodo.org/records/8339691>
- 확인 수준: 레코드 메타데이터와 배포 파일 11개를 직접 확인함
- 사용 파일: `CEAS_08`, `Enron`, `Ling`, `Nazario`, `Nazario_5`, `Nigerian_5`,
  `Nigerian_Fraud`, `SpamAssasin`, `TREC_05`, `TREC_06`, `TREC_07` (CSV 11개)
- 전체 파일을 Zenodo API가 명시한 바이트 크기와 비교해 일치를 확인했다
- 라이선스: `TBD` (레코드 라이선스 표기 재확인 필요)

CSV 11개를 **하나의 출처**로 합쳤다. 이유는 두 가지다.

1. TREC_05/06/07이 서로 많이 겹친다. 출처를 나누면 같은 메일이 train과 test에 동시에 들어간다.
   하나로 합치면 중복 제거가 걸려 9,892건이 제거됐다.
2. 11개를 따로 두면 전체 15개 출처 중 11개가 피싱이라 출처별 가중치를 지배한다.

원래 파일명은 `corpus`, 원래 스팸/피싱 라벨은 `phishing_label` 메타데이터로 보존했다.
그룹은 정규화한 제목(소문자·영숫자만, 16자 이상) 기준으로 묶어 같은 스팸 캠페인이 분할을
넘나들지 않게 했다. 제목이 짧거나 비면 행 단위로 묶는다.

**이 데이터는 `prompt_injection=0`이지만 안전한 메일이 아니다.** 프롬프트 인젝션이 아니라는
뜻일 뿐이며, 상당수가 스팸이나 피싱이다. 탐지기가 "피싱 문체"를 인젝션으로 오인하지 않도록
하는 hard negative로 사용한다.

### BIPIA EmailQA

- 출처: <https://github.com/microsoft/BIPIA>
- 고정 커밋: `a004b69ec0dd446e0afd461d98cb5e96e120a5d0`
- 사용 파일: `benchmark/email/train.jsonl`, `benchmark/email/test.jsonl`,
  `benchmark/text_attack_train.json`, `benchmark/text_attack_test.json`
- 정상 메일 78건(중복 제거 후), 공격 문구 15개 범주 150종

**BIPIA는 더 이상 독립 외부 테스트가 아니다.** 이전 모델 평가와 임계값 조정에 이미 사용했기
때문에 개발 데이터로 간주하고 학습·검증·내부 테스트에 편입했다.

생성 방식에서 두 가지를 바로잡았다.

1. **직렬화 해제.** BIPIA는 메일을 `SUBJECT: ...|EMAIL_FROM: ...|CONTENT: ...` 한 줄로
   저장한다. 이 파이프 구분자 표시는 다른 출처에 전혀 없어서, 문자열을 통째로 본문에 넣으면
   모델이 공격 문구가 아니라 "이 메일은 BIPIA 것"이라는 데이터셋 지문을 읽는다. 제목·발신자·본문
   필드로 다시 파싱해 다른 출처와 같은 형태로 넣고, 공격 문구는 본문에만 삽입한다.
2. **정상 메일과 공격 운반 메일 분리.** 같은 메일을 정상으로도 쓰고 공격 운반체로도 쓰면 각
   메일이 정상 1건 대 공격 약 6건으로 등장해, 모델이 그 메일 자체를 공격으로 암기한다.
   실제로 학습에 사용한 정상 52건 중 48건이 공격으로 분류됐다. 일반화 실패가 아니라 학습
   자체가 되지 않은 상태였다. 분할마다 메일의 절반은 정상 전용, 절반은 공격 운반 전용으로
   나눠 어떤 메일도 양쪽 라벨을 동시에 갖지 않게 했다.

전체 조합(문맥 78 × 공격 150 × 위치 3)은 사용하지 않는다. 그러면 메일 78건에서 약 17,550건이
나오고 정상:공격 비율이 1:300이 되어 어떤 가중치로도 교정되지 않는다. 현재는 공격 문구 150종
각각을 시작·중간·끝 3곳에 삽입하고 운반 메일을 돌려 쓴다(450건). **공격 문구와 정상 메일은
전부 사용한다.** 원본 메일과 공격 문구를 각각 먼저 분할한 뒤 같은 분할끼리만 조합해 누출을
막는다. 중간 삽입은 별도 NLTK 의존성을 피하기 위해 문자열 중앙 이후 첫 공백을 사용한다.

## 출처·클래스 가중치

한 출처가 모델을 지배하지 않도록 `(출처, 라벨)` 셀 단위로 가중치를 준다.

- 셀 크기의 **제곱근**으로 감쇠한다. 감쇠 없이 두면 LLMail의 공격 20만건이 나머지를 덮고,
  완전히 균등화하면 수백 건 규모의 셀이 행당 가중치 140에 도달해 점수가 0과 1로 포화되며
  ROC AUC가 3포인트 떨어졌다.
- 그 위에서 두 클래스의 전체 질량을 같게 맞춘다.
- 행당 가중치는 **32배로 상한**을 둔다. LLMail의 정상 FP 메일 160건과 공격 20만건을 정확히
  맞추려면 정상 1건이 보통 메일 100건 이상의 무게를 갖게 되어 모델이 다시 포화된다.

| 셀 | 행당 가중치 |
| --- | ---: |
| bipia-emailqa 정상 | 32.000 (상한) |
| llmail-inject 정상 | 24.887 |
| bipia-emailqa 공격 | 18.284 |
| cw-l-email-corpus 정상 | 8.693 |
| paired-email 공격 | 5.985 |
| paired-email 정상 | 4.865 |
| llmail-inject 공격 | 1.018 |
| phishing-curated 정상 | 0.693 |

### 검토했다가 채택하지 않은 방식

출처 **안에서** 정상과 공격 질량을 정확히 1:1로 맞추는 방식을 실험했다. BIPIA 정상 오탐은
개선됐지만(학습 48/52 → 3/52) 정상 메일 통과율이 98%에서 **37%** 로 무너졌다. 작은 출처의
공격 쪽이 굶어 safe 임계값이 0으로 끌려간 결과다.

이 두 조건은 **수학적으로 양립할 수 없다.** 정상만 있는 출처(phishing-curated, cw-l)가 정상
질량의 68%를 차지하므로, "모든 출처가 내부적으로 균형"과 "전역 클래스 균형"을 동시에 만족하는
해가 존재하지 않는다. 전역 균형을 택하고 BIPIA 쪽은 데이터 생성 단계에서 바로잡았다.

## 모델 입력과 특징

- 공통 입력: 제목, 발신자, plain 본문, HTML 원문, HTML에서 추출한 텍스트
- `.eml` 직접 검사는 수신자와 Reply-To 헤더도 입력에 포함한다
- 단어 특징: 1~2-gram 해시, 2^20 버킷
- 문자 특징: 3~5-gram(`char_wb`) 해시, 2^20 버킷
- 두 특징 모두 binary + L2 정규화. 해시 특징에는 IDF 가중이 없다
- 분류기: `SGDClassifier(loss="log_loss", alpha=1e-5, average=True)`, `partial_fit` 3 epoch
- 학습 라이브러리: scikit-learn 1.6.0
- 출력: 인젝션 확률, 의심·위험 임계값, `safe`·`suspicious`·`danger`

헤더 값에 포함된 개행과 NUL 문자는 공백으로 평탄화한다. LLMail의 제목은 공격자가 작성한
값이라 개행이 들어 있고, 그대로 두면 메일 직렬화 단계에서 예외가 발생한다.

### `alpha` 선택 근거

| alpha | validation ROC AUC | 의심/위험 임계값 | test 정상 통과율 |
| ---: | ---: | --- | ---: |
| 1e-6 | 0.99879 | 3e-06 / 0.99999 | 98.46% |
| **1e-5** | **0.99953** | **0.072 / 0.745** | **98.48%** |
| 1e-4 | 0.99963 | 0.262 / 0.544 | 98.24% |

(위 표는 LLMail phase2만 사용한 13.2만건 예비 말뭉치 기준이다.)

1e-6에서는 점수가 정확히 0과 1로 포화되어 임계값이 `3e-06`과 `0.99999`로 잡혔고 의미를
잃었다. 1e-4는 보정이 가장 좋지만 정상 통과율이 낮다. 1e-5를 선택했다.

### 임계값 산정

| 단계 | 기준 | 값 |
| --- | --- | ---: |
| `suspicious` | validation 공격의 safe 누락률 0.5% 이하를 만족하는 최대 점수 | 0.338996 |
| `danger` | validation 정상 오탐률 0.2% 이하에서 공격 재현율이 가장 높은 점수 | 0.414419 |

두 단계에 같은 예산(정상 오탐 2%)을 쓰면 `danger`가 재현율을 최대화하느라 조건을 만족하는
가장 낮은 점수로 내려가고, `suspicious`는 올라가서 두 값이 겹친다. 실제로 그 결과가 나와
`suspicious` 구간이 사라졌다. 그래서 `danger`에 더 엄격한 별도 예산 0.2%를 준다.
`--max-validation-fpr`(2%)은 safe 게이트의 정상 검토 예산으로 보고만 하고 강제하지 않는다.

현재 모델의 validation 점수 분포는 다음과 같아 두 임계값이 분포 사이 빈 구간에 위치한다.

| 백분위 | 정상 | 공격 |
| --- | ---: | ---: |
| p50 | 0.00181 | 0.99877 |
| p95 | 0.04300 | 0.99999 |
| p99 | 0.14798 | 1.00000 |
| p99.5 | 0.24162 | 1.00000 |
| p1 | 0.00002 | 0.49562 |

Gmail 수집 API의 `subject`, `sender`, `text_plain`, `text_html`을 메모리에서 변환한다. 수집 계약에
`reply_to`가 없으므로 Gmail 연동에서는 Reply-To를 사용하지 않고, `.eml` 직접 검사에서만 분석한다.
실제 메일 원문과 변환 결과는 저장하지 않는다. `warnings`가 있거나 `truncated`가 참이면 모델
판정과 별도로 "수집 불완전"을 유지한다.

## 포함된 공격 유형

- 기존 지시 무시와 새 역할 부여
- 메일 전송 등 도구 호출 유도
- 다른 메일·내부 정보의 외부 전송 유도
- 시스템/사용자 구분자와 가짜 지시 블록 삽입
- 공백·기호·반복어를 이용한 난독화
- 정상적인 권한 요청처럼 보이는 문맥·권위 조작
- 출력 조작(역순 답변, 다른 언어 답변, 특정 문장 삽입 요구)

샘플은 공개 연구 데이터 또는 합성 데이터이며 실제 사용자 메일은 포함하지 않는다. 공격 자동화나
실제 계정 대상 시험에는 사용하지 않는다.

## 일반화 성능 해석

**내부 test 공격 누락률 0.805%를 일반화 성능으로 제시하면 안 된다.** test 공격 31,182건 중
30,407건(97.5%)이 LLMail이므로 사실상 LLMail 분포 안의 분리 성능이다.

| 평가셋 | 공격 safe 누락률 | 공격 문구 |
| --- | ---: | --- |
| 내부 test 중 LLMail | 0.73% (222/30,407) | 같은 분포 |
| 내부 test 전체 | 0.805% (251/31,182) | 대부분 LLMail |
| 내부 test 중 BIPIA | 34.7% (26/75) | 홀드아웃 25종 |
| InjecAgent Gmail | 0% (0/124) | 완전 외부, 공격만 있음 |
| KoPI-Bench 한국어 메일 후보 | 0% (0/1,572) | 정상 검토율 100%(1,234/1,234) |

InjecAgent 공격을 모두 검토 대상으로 올린 사실만으로 일반화 성능이 좋다고 결론 내릴 수 없다.
정상 사례가 없어서 외부 오탐률을 계산할 수 없고, 한국어 보조 평가에서는 정상 메일도 전부
검토 대상으로 올렸다. 현재 `0.05` 운영 경계는 외부 분포에서 `safe` 통과 기능을 하지 못한다.

## 이전 기준 모델과의 비교

| 항목 | 이전 기준 모델 | 현재 모델 |
| --- | --- | --- |
| 학습 데이터 | 24,488건(LLMail 가공본 + Paired) | 421,812건(5개 출처) |
| 특징 | TF-IDF 단어·문자 n-gram | 해시 단어·문자 n-gram(2^20 버킷) |
| 학습 | 전량 메모리 적재 | 디스크 스트리밍 + `partial_fit` |
| 분할 | 전체를 70/15/15 | 출처별 그룹 2/3 · 1/6 · 1/6 |
| 가중치 | `class_weight="balanced"` | 출처·클래스 셀 제곱근 감쇠 + 상한 32 |
| 의심/위험 임계값 | 0.040019 / 0.088772 | 운영 0.05 / 0.414419(학습 0.338996 / 0.414419) |
| BIPIA 정상 오탐률 | 100% (44/44) | 개발 데이터로 편입(아래 한계 참조) |

이전 모델의 BIPIA 정상 오탐률 100%는 결제·영수증·연락처·권한 표현을 포함한 정상 hard
negative가 학습에 없었던 것이 원인이었다. 이번에 phishing-curated 208,298건을 hard negative로
넣어 test ham 오탐률을 0.25%로 낮췄다.

이전 결과 기록은 `src/detector/reports/bipia-emailqa-metrics.json`과
`llmail-external-metrics.json`에 남겨 두었다. 이 보고서를 생성한 스크립트
(`evaluate_bipia.py`, `prepare_llmail_split.py`)는 이전 분할 체계를 전제하므로 삭제했다.
현재 상태에서 그대로 실행하면 BIPIA가 학습 데이터인 채로 누출된 수치가 나온다.

## 알려진 한계와 사용 범위

1. **결합 탐지는 외부 분포에서 공격과 정상을 함께 검토 대상으로 올린다.** 최종 판정 기준으로
   InjecAgent와 KoPI-Bench 공격은 미탐 0%였지만 KoPI-Bench 정상도 전부 검토 대상이 됐다.
   원인 진단으로 구성요소를 나눠 보면 #31 Transformer는 두 데이터셋 공격을 모두 `safe`로
   분류해 최종 판정을 한 건도 바꾸지 못했고, 결과는 전부 TF 계열 쪽에서 결정됐다.
2. **BIPIA 정상 메일은 38건(test 6건)** 이라 오탐 측정값으로 사용할 수 없다. 정상 오탐의
   실질 근거는 phishing-curated test ham 33,761건, cw-l 220건, paired 700건이다.
3. **LLMail 라벨은 공격 시도 기준이다.** 중복 제거 후 203,150건 중 exfil 목표를 달성한 것은
   약 12%이고 나머지는 실패한 시도다. `exfil_sent` 메타데이터로 재판단할 수 있다.
4. **분할 간 샘플 수가 고르지 않다.** LLMail 팀 크기가 멱법칙이라 validation 114,322건,
   test 65,896건이다. 그룹 수는 정확히 2/3 · 1/6 · 1/6이다.
5. **피싱 데이터는 안전한 메일이 아니다.** `prompt_injection=0`은 프롬프트 인젝션이 아니라는
   뜻일 뿐이며, 원래 스팸·피싱 라벨은 `phishing_label`로 보존했다.
6. **BIPIA는 외부 테스트가 아니다.** 이전 모델 평가와 임계값 조정에 이미 사용했다.
7. **한국어 독립 평가셋이 없어 한국어 공격 탐지 성능은 아직 측정하지 않았다.**
8. 모델은 메일 문자열만 보고 사용자의 실제 위임 범위나 조직 정책을 알지 못한다.
9. 이미지, OCR, 첨부파일 내용은 분석하지 않는다.
10. `safe`는 안전 보장이 아니라 정적 분석 범위에서 인젝션을 탐지하지 못했다는 뜻이다.
11. 높은 데이터셋 점수를 실제 서비스 성능이나 안전 보장으로 표현하지 않는다.
12. 모델 결과만으로 메일을 자동 차단하거나 에이전트의 도구 실행을 허가하지 않는다.
