# 한국어 짝 구성 코퍼스 (`kopi-email-paired.jsonl`)

이슈 [#84](https://github.com/ProDog-2026/workspace/issues/84). 생성 스크립트는
[`../../src/detector/scripts/build_korean_paired_corpus.py`](../../src/detector/scripts/build_korean_paired_corpus.py),
생성 기록은 [`../../src/detector/reports/korean-paired-corpus-manifest.json`](../../src/detector/reports/korean-paired-corpus-manifest.json)이다.

## 왜 만들었나

기존 코퍼스 `kopi-email-cleaned.jsonl`(2,773행)은 `인젝션`이 "거래 알림 + 주제 밖 한 줄",
`정상`이 "같은 알림에서 그 줄만 없는 것"인데 **운반 메일 하나당 라벨이 하나뿐**이었다.
그래서 모델이 "붙은 줄이 지시문인가"를 배우지 않고 "이 운반 틀이 정상으로 본 것인가"를
외웠다(shortcut learning).

2026-11-19 진단에서 다음 가설을 차례로 배제하고 이 결론에 도달했다.

| 가설 | 판정 | 근거 |
| --- | --- | --- |
| 숨긴 텍스트 추출 실패 | 아님 | 공격 문구는 세 건 다 `[HTML_RAW]` 경유로 모델 입력에 들어간다 |
| 학습·추론 포맷 불일치 | 아님 | 학습과 같은 `fields_to_model_text` 포맷으로 넣어도 0.0074 이하 |
| 256토큰 절단으로 꼬리 잘림 | 아님 | 170~190토큰으로 한계 안이고 공격 문구가 보존된다 |
| 운반 텍스트가 공격 신호를 덮는다 | **맞음** | 아래 |

- 같은 공격 문구가 PDF 추출 텍스트에서는 0.9906, 문구만 제거하면 0.0426으로 떨어진다.
  모델에 신호 자체는 있다.
- 토큰 수가 거의 같은(173 vs 170) 메일 본문에 같은 문구를 넣으면 0.0074다. 차이는 운반 텍스트뿐.
- 홀드아웃 3종의 운반 메일이 기존 학습 코퍼스에 `정상` 라벨로 존재했다
  (원본 표 CSV 45행 → train, 118행 → validation, 123행 → test).
- 임계값으로 고칠 수 없었다: 공격본 점수가 대조군보다 **낮았다**
  (01 0.0181 vs 0.0417, 02 0.0032 vs 0.0421). 순위 역전이라 어떤 임계값도 분리하지 못한다.

## 어떻게 만들었나

모든 운반 메일이 `정상`과 `인젝션` 양쪽에 모두 등장하게 짝지었다. 운반 텍스트가 두 라벨에
똑같이 나타나므로 라벨 단서로 쓸 수 없다.

| 짝 만드는 방법 | 행 수 |
| --- | ---: |
| 공격 문구 위치를 아는 인젝션 → 원본 그대로 공격본 | 851 |
| 위와 같은 행 → 문구만 떼서 정상본 | 851 |
| 원래 정상 행 → 그대로 정상본 | 1,153 |
| 위와 같은 행 → 문구 풀에서 골라 삽입해 공격본 | 1,153 |
| **합계** | **4,008** |

- 삽입 문구는 **코퍼스 안에 이미 있는 136종**에서만 고른다. 새 문구를 지어내지 않았다.
  문구 유형 다양화(지시형 추가)는 별도 이슈로 다룬다.
- 삽입 위치는 원본에서 관찰한 분포(앞 350 · 중간 292 · 뒤 209)를 따라 뽑는다.
- `seed=42`로 고정해 재현된다.

### 제외한 행

| 사유 | 행 수 |
| --- | ---: |
| 공격 문구 위치 미확인 | 701 |
| 홀드아웃 운반 메일 (원본 표 45 · 118 · 123행) | 3 |

공격 문구 위치를 모르면 같은 운반의 정상본을 만들 수 없다. 운반이 한쪽 라벨로만 남으면
고치려는 shortcut이 그대로 돌아오므로 버렸다.

홀드아웃 운반 메일을 뺀 이유는 따로 있다. 그 메일이 `정상` 라벨로 train에 들어 있던 것이
01_white_text 미탐의 직접 원인이었다. 빼야 홀드아웃이 처음 보는 메일로 남는다.

## 분할

분할은 기존 `train_korean_detector.py`의 `template_key`·`split_rows`를 그대로 쓴다. 이 함수가
공격 문구를 뗀 본문으로 그룹 키를 만들기 때문에, 짝의 두 행은 같은 키를 갖고 반드시 같은
분할에 들어간다. 분할 코드는 수정하지 않았다.

| 분할 | 행 | 인젝션 | 정상 |
| --- | ---: | ---: | ---: |
| train | 2,804 | 1,402 | 1,402 |
| validation | 602 | 301 | 301 |
| test | 602 | 301 | 301 |

세 분할 모두 정확히 50:50이다. 짝이 쪼개지지 않았다는 뜻이다.

## 스키마

입력 코퍼스와 같은 필드에 `pair_origin` 하나만 더했다. 그래서 학습 스크립트는
`--cleaned docs/dataset/kopi-email-paired.jsonl --conflicts NONE`만 주면 그대로 읽는다.
라벨 충돌 행은 생성 단계에서 이미 제외했다.

| 필드 | 내용 |
| --- | --- |
| `source_rows` | 원본 표 CSV 행 번호 |
| `selection` | 원본 코퍼스에서 그대로 승계 |
| `original_label` | `인젝션` 또는 `정상` |
| `attack_position_status` | 공격본은 `짝 구성`, 정상본은 `해당 없음` |
| `suspected_attack_phrase` | 공격본에만 채운다. 정상본은 빈 문자열 |
| `mail_text` | 메일 본문 |
| `pair_origin` | `원본 공격` · `공격 문구 제거` · `원본 정상` · `문구 삽입(앞/중간/뒤)` |

`suspected_attack_phrase`를 공격본에만 남기는 것이 분할 묶음의 전제다. 정상본에 이 값을
채우면 `template_key`가 달라져 짝이 쪼개진다.

## 생성과 검증

```powershell
python src/detector/scripts/build_korean_paired_corpus.py
```

스크립트가 생성 직후 다음을 assert로 검사한다. 하나라도 깨지면 파일을 쓰지 않는다.

- 라벨이 정확히 반반인지
- 모든 고유 운반 메일이 `정상`과 `인젝션` 양쪽에 다 있는지
- 정상본에 공격 문구가 남지 않았는지, 공격본에는 문구가 실제로 들어 있는지
- 홀드아웃 운반 메일이 남지 않았는지
- 기록한 고유 운반 수가 실제와 맞는지

## 한계

- **정상본·공격본 중 절반은 합성이다.** 문구를 떼거나 붙여 만들었으므로 실제 수신 메일이
  아니다. 운반 shortcut을 없애는 목적에는 맞지만, 문구 삽입 위치와 줄바꿈 처리가 실제 공격의
  표면과 다를 수 있다.
- **공격 문구가 136종뿐이고 유형이 좁다.** 대부분 "주제 밖 질문·요청"이다. 답변 자체를 지정하는
  지시형(예: 금액을 다르게 답하게 유도)은 거의 없다. 이 유형 편중은 이 코퍼스로 해결되지 않는다.
- **HTML이 전혀 없다.** 학습 입력은 `fields_to_model_text(body_text=...)`로 만든 평문 본문뿐이라
  `[HTML_RAW]`·`[HTML_TEXT]` 구간을 모델이 본 적이 없다. HTML 주석에만 공격이 들어 있는
  사례(02_html_comment)는 이 코퍼스로 학습해도 어렵다.
- **고유 운반 메일은 1,290개다.** 같은 운반에 다른 문구가 붙은 행이 있어 4,008행보다 훨씬 적다.
  실제 다양성은 행 수가 아니라 이 숫자로 읽어야 한다.
