# 1차 메일 분류 → 동적 검사 연결과 사용법

갱신일: 2026-11-09 · 관련 작업: [Issue #52](https://github.com/ProDog-2026/workspace/issues/52)

## 목적과 범위

Gmail 메일의 1차 분류가 `suspicious` 또는 `danger`이면 기존 `src/agent-container` 실행기에 전달하고, 진행 상태와 실행 증거를 React 대시보드에서 확인한다. 대시보드는 1차 판정과 최신 동적 관찰을 함께 사용해 최종 판정을 표시한다. 1차 판정과 정적 점수는 근거로 남긴다.

```text
React 받은편지함 → Gmail 수집·1차 분류
                     ├─ safe                → 1차 결과 표시
                     ├─ suspicious / danger → 인증된 POST → 동적 대기열
                     │                                      ↓
                     │                            agent-container 제어 API
                     │                                      ↓
                     │                            작업 Docker 컨테이너
                     │                                      ↓
                     └──────────────────────────── 진행·결과·증거 표시
```

자동 전달은 사용자가 받은편지함에서 조회해 불러온 메일에 적용된다. 다음 페이지를 불러오면 그 페이지의 대상도 등록된다. 전체 Gmail을 백그라운드에서 상시 감시하는 기능은 아니다. `safe`는 1차 검사 범위의 결과이며, 분류기가 미설정이거나 실패한 메일에는 판정을 만들어 전달하지 않는다.

자동 격리·삭제·차단, 첨부파일 실행, 외부 LLM 공급자 연동, 새로운 최종 점수 산식은 이 연결 범위에 포함하지 않는다.

## 서비스 연결과 저장

- React 대시보드는 Gmail 백엔드의 `/api/dynamic/*`만 호출한다. Gmail 백엔드가 로컬 제어 API `http://127.0.0.1:8000`에 HTTP로 연결한다.
- 메일 목록 GET은 실행을 시작하지 않는다. 자동 전달은 별도의 `POST /api/dynamic/mail/{message_id}`로 요청한다. 서버는 세션·Origin·CSRF를 확인하고 해당 계정의 메일과 1차 판정을 다시 조회한다. 브라우저가 본문이나 판정을 지정하지 않는다.
- 사용자가 수동으로 선택한 메일은 별도의 `POST /api/dynamic/manual-mail/{message_id}`로 요청한다. 연결된 계정과 CSRF를 확인하고 메일을 서버에서 다시 가져오며, 1차 분류를 수행하거나 판정을 만들지 않는다. 자동 전달 기록과 구분한다.
- Gmail 백엔드는 대기열을 관리하고 한 번에 한 작업을 실행한다. 계정, 메일 ID, 본문 해시, 실행 설정, 프롬프트 내용 해시로 중복을 구분한다. 같은 조건의 재조회는 기존 기록을 재사용하며, 명시적 재검사는 이전 증거를 남긴 새 기록이 된다.
- 실행 요청에는 안정적인 `request_id`를 사용한다. 접수 응답이 유실돼도 같은 식별자로 확인하며 새 ID로 중복 실행하지 않는다. 접수 여부가 불확실하면 실행 슬롯을 유지한다.
- Gmail DB는 설정·작업 소유자·실행 식별자·1차 판정·검사 범위 경고를 보관한다. 결과 본문·요약·이벤트는 제어 API에서 조회한다. Gmail 백엔드를 다시 시작해도 저장된 식별자로 진행 중이던 실행을 확인한다.

핵심 구현은 `src/gmail/src/prodog_gmail/dynamic.py`, `dynamic_api.py`, `dynamic_models.py`, `dynamic_store.py`와 `src/dashboard/src/Dynamic.jsx`, `useDynamicInbox.js`에 있다. 기존 실행·증거 판정은 `src/agent-container/control-dashboard/backend/`를 재사용한다.

## 새 대시보드 사용법

새 화면은 [동적 검사 페이지](http://127.0.0.1:5173/#/dynamic)에 있다. Gmail 연결은 기존 **설정** 화면에서 진행한다.

**동적 검사 실행 환경**에서 Docker, 이미지, 검사 서버와 수신 서버 상태를 확인할 수 있다. 준비되지 않았다면 **이미지 배포 및 서버 실행**을 누르면 로컬 Compose 이미지를 빌드하고 서비스를 실행한다. 완료 후 서버 연결을 확인하며, 모델이 선택되어 있다면 Ollama 연결 및 도구 호출도 확인한다. Docker Desktop은 미리 실행되어 있어야 한다. 실행 중이거나 상태가 불확실한 검사가 있으면 배포를 거절하며, 대기 중인 검사는 배포가 끝날 때까지 기다린다. 관련 작업: [Issue #53](https://github.com/ProDog-2026/workspace/issues/53).

1. **모델 연결 및 자동 검사**에서 Ollama 주소와 설치된 모델, 시스템 프롬프트, 온도, 호출·토큰·시간 한도를 선택한다. 모델은 자동 선택하지 않는다. **모델 목록 새로고침**과 **연결·도구 호출 확인**으로 연결을 확인한 뒤 **설정 저장**을 누른다.
2. **의심·위험 메일 자동 전달**을 켜고 받은편지함을 열면, 성공한 1차 검사에서 의심·위험인 메일을 등록한다. 메일 목록과 상세 화면에서 동적 상태를 함께 보고 **동적 검사 결과·근거 보기**로 해당 실행을 연다.
3. **프롬프트 보기·수정**에서는 목록과 본문을 보고 새 프롬프트를 만들 수 있다. 여기서 본인이 만든 프롬프트는 수정·삭제할 수 있다. 프롬프트 선택을 자동 검사에 적용하려면 설정도 저장한다.
4. **수동 실험 · 내 메일 선택 또는 직접 입력**에서 받은편지함 목록을 불러와 메일을 선택하거나 제목·본문을 직접 입력한다. 선택한 메일 한 건만 1차 분류 없이 실행하고, 기록에 수동 검사임을 표시한다. 더 오래된 메일은 **메일 더 불러오기**로 조회한다.
5. **실행 내역**에서 실행을 선택하면 분석 결과·요약, 도구 요청과 효과, 데이터 흐름의 노드·단계별 상태, 이벤트 로그와 근거를 볼 수 있다. 진행 중인 작업은 **검사 중지**, 종료된 Gmail 검사는 허용되는 상태에서 **현재 설정으로 재검사**를 사용할 수 있다.

### 기존 실험 대시보드에서 옮기기

- 기존 제어 서버의 연결 설정은 메모리에 보관하던 값이다. 새 화면에서 모델·한도 등을 선택하고 다시 저장한다. 이전 화면의 모델 선택을 새 계정 설정으로 자동 이관하지 않는다.
- **기존 실험 기록 불러오기**로 제어 서버에 보관된 기존 실행을 새 화면에 연결한다. 이미 Gmail 작업에 연결된 실행을 다른 계정의 기록으로 가져오지 않는다.
- 기본 프롬프트와 기존 실험실에서 만든 사용자 프롬프트는 볼 수 있지만 새 화면에서 바로 덮어쓰지 않는다. 수정하려면 새 ID로 복사해 저장한 뒤 선택한다.

## 입력 데이터와 판정 해석

`email.subject`에는 제목을, `email.body`에는 고정된 `UNTRUSTED EMAIL DATA` 구획 아래 발신자와 `analysis_text`를 전달한다. HTML 원문과 주석도 텍스트로 보존한다. 메일 내용은 시스템 프롬프트나 모델 연결 설정으로 사용하지 않는다. 모델·주소·프롬프트·실행 한도는 설정 화면에서 저장한 값을 사용한다.

`body_hash`, 수집 경고, 본문 잘림, 첨부파일 제외 여부, 1차 판정은 작업에 함께 보관한다. Google OAuth 토큰, 세션 쿠키, 서비스 키는 동적 실행 입력으로 전달하지 않는다.

| 상황 | 동적 표시·해석 | 대시보드 최종 판정 |
|---|---|---|
| 1차 정상 | 자동 전달 대상 아님 | 유지 |
| 대기·실행 중 | 검사 대기·검사 중 | 유지 |
| 이탈 또는 효과 증거 있음 (`observed`) | 이상 행동 관찰 및 근거, 실행 완료 여부 별도 표시 | 1차 의심을 위험으로 승격, 1차 위험 유지 |
| 완료, 이탈·효과 증거 없음 | 이번 실행에서 이상 행동 미관찰 | 1차 판정 유지 |
| 시간 초과·중지·검증 실패, 관찰된 증거 없음 | 미완료 또는 실패 | 1차 판정 유지 |
| 서비스 접속 실패·접수 여부 불명 | 연결 확인 필요, 결과 미확정 | 유지 |

`send_email`은 모의 실행이며 실제 메일 전송으로 표시하지 않는다. 동적 증거를 임의의 `llm_score`나 분류 확률로 변환하지 않는다. 본문 잘림과 첨부파일 제외 경고는 완료 뒤에도 표시한다.

## 로컬 실행

Docker Desktop의 Linux 컨테이너 모드, 호스트 Ollama와 도구 호출을 지원하는 설치 모델, Python/uv, Node/npm이 필요하다. 각 명령은 표시된 폴더에서 실행한다. 세부 환경 준비는 [Gmail README](../src/gmail/README.md)와 [실행기 README](../src/agent-container/README.md)를 따른다.

### 1. 실행기 갱신

`src/agent-container`에서 실행한다. `request_id` 지원이 추가된 제어 API를 사용해야 하므로 기존 컨테이너도 다시 빌드한다.

```powershell
docker build -t agent-container-control -f control-dashboard/Dockerfile control-dashboard
docker build -t agent-container-receiver -f control-dashboard/receiver/Dockerfile control-dashboard
docker build -t agent-container-worker:phase1 -f agent-container/Dockerfile .
docker compose --project-name agent-container up -d --no-build
```

이미지는 고정된 프로젝트 내부 컨텍스트로 각각 빌드한다. Compose Bake가 일부 macOS 환경에서 불필요한 `fs.read` 권한을 요구하는 문제를 피하며, 파일시스템 권한 검사를 해제하지 않는다. Compose가 작업 이미지 준비 서비스도 의존성으로 실행한다. Ollama가 호스트에서 실행 중인지 확인한다. Docker 내부에서 호스트 Ollama에 연결할 때는 일반적으로 `http://host.docker.internal:11434`를 사용한다.

### 2. Gmail 백엔드

`src/gmail/.env`에서 다음 연결값을 확인한다. 기존 OAuth 설정과 암호화 키는 유지한다.

```dotenv
DYNAMIC_SERVICE_URL=http://127.0.0.1:8000
DASHBOARD_URL=http://127.0.0.1:5173
```

`src/gmail`에서:

```powershell
uv sync --frozen --dev
uv run python scripts/setup_local.py
uv run uvicorn prodog_gmail.app:app --host 127.0.0.1 --port 8765 --no-access-log
```

`setup_local.py`는 기존 `.env`를 덮어쓰지 않는다. `DETECTOR_MODEL_PATH`에는 별도로 준비한 1차 분류기 파일 경로가 필요하다. 이 PC의 확인 시점에는 해당 값이 비어 있고 workspace에 학습 가중치가 없다. 따라서 현재 실제 Gmail 메일의 자동 전달을 사용하려면 먼저 분류기 파일을 연결해야 한다. 동적 페이지의 합성 메일 수동 실험은 별도로 사용할 수 있다.

### 3. React 대시보드

별도 터미널의 `src/dashboard`에서:

```powershell
npm install
npm run dev
```

[새 대시보드](http://127.0.0.1:5173/)를 연다. 개발 서버는 `/api`와 `/oauth`를 Gmail 백엔드로 전달한다. 세션을 공유하도록 `localhost` 대신 `127.0.0.1` 주소를 사용한다.

### 종료와 불확실한 실행 처리

직접 실행한 Gmail·Vite 터미널은 `Ctrl+C`로 종료하고, 실행기 폴더에서는 다음 명령으로 컨테이너를 중지한다.

```powershell
docker compose stop --timeout 10
```

Gmail을 기존 백그라운드 시작 스크립트로 띄웠다면 `src/gmail/stop.ps1`을 사용한다. 다른 작업의 서버나 Ollama까지 일괄 종료하지 않는다.

제어 서버가 실행 중 재시작되어 실제 컨테이너 상태를 확인할 수 없으면 접수 예약을 유지하고 대기열을 보류한다. 실행 기록이 없다는 응답만으로 미접수라고 판단하거나 새 ID로 재실행하지 않는다. 운영자가 기존 컨테이너와 보관 증거를 확인해 실행 상태를 정리한 뒤 재개해야 한다. 대기열을 강제로 풀기 위해 기록만 삭제하면 중복 실행과 증거 연결 손실이 생길 수 있다.

## 검증 범위와 자료 취급

합성 입력과 대체 분류기를 사용하는 자동 테스트로 정상 메일 제외, 의심·위험 전달, 중복 억제, 계정 분리, 미완료·오류 표시를 확인했다. 프런트엔드 상태 표시 테스트와 빌드도 확인했다. 이는 학습 모델의 탐지 성능 검증이 아니다.

실제 Docker 실행에서는 `qwen3.5:4b`로 합성 메일 수동 실험을 완료하고 요약·증거, 데이터 흐름 14단계와 이벤트 로그 15건을 확인했다. 이 모델명은 해당 검증에서 사용한 값이며 앱의 자동 기본 선택이 아니다. 이 확인은 실제 컨테이너 실행과 화면 연결에 대한 것으로, 컨테이너 보안 격리·네트워크 차단을 검증한 결과가 아니다. 격리 검증은 실행기 README의 Docker 통합 테스트와 `scripts/check_network.py` 절차가 별도로 필요하다.

Gmail DB에는 메일 본문·RAW·요약·이벤트 내용을 저장하지 않는다. 대기 중 본문은 메모리에 두며, 재시작 후 필요한 Gmail 입력은 다시 조회한다. 반면 실행기의 `data/runs/`에는 이벤트·결과·요약을 보관하므로 메일 내용과 모델 출력이 포함될 수 있다. Gmail 수집 단계의 본문 미저장 조건을 실행기까지 확대해 설명하면 안 된다. 실제 메일, `.env`, OAuth 자격 증명과 실행 자료는 Git에 포함하지 않으며 검증에는 합성 메일을 사용한다.

Gmail 어댑터의 계정별 권한 검사와 별개로 기존 제어 API는 로컬 실험용이다. 제어 API를 공유 서버나 공개 주소로 노출하는 구조는 이 통합의 범위 밖이다.
