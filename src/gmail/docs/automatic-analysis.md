# 수집 → 정적 분류 → Ollama 동적 분석

대시보드가 메일을 수집하면 정적 분석을 자동 실행한다. 계정별 자동 분석 설정은 후속 동적 실행에 적용한다.
메일별 실행 버튼은 필요 없다. 처음 한 번 설정에서 사용할 모델과 자동 분석 사용을 저장한다.
현재 자동 경로는 **Ollama만 사용**하며, 외부 API나 유료 모델로 자동 전환하지 않는다.
동적 분석 메뉴는 결과 조회 전용이다. 대기·실행 기록, 명령·출력·파일 변경을 확인하고
진행 중인 실행을 중지하거나 결과 JSON을 내려받을 수 있다. 수동 입력·실행 폼은 제공하지 않는다.

## 최초 준비

1. 팀의 `feature/31-transformer-ensemble`에서 가져온 실제 가중치를 사용한다.
   `src/detector/models/prompt_injection.joblib`과 `models/quadrat-transformer/`를
   [팀 모델 공유 페이지](https://app.notion.com/p/40714dd1c3c48153b351f8fd6c01855d)에서 받아 배치한다.
   로컬 파일은 유지하지만 최신 develop 정책에 따라 Git에서는 제외한다.
   가져온 팀 커밋은 `3e8968e`다. joblib은 Python 객체를 로드하므로 출처를 모르는 파일은
   사용하지 않는다. 임의 샘플 모델로 대체하지 않는다.
2. 정적 탐지기 전용 Python 3.12 환경을 준비한다. Gmail의 Python 3.14 환경과 분리한다.

```bash
cd ~/Downloads/캡스톤/workspace/src/detector
uv sync --python 3.12 --extra transformer --dev
```

Windows도 본인 체크아웃의 `src/detector`에서 같은 명령을 실행한다.
scikit-learn 1.6.0과 PyTorch·Transformers를 사용한다. 다른 환경·모델은 `src/gmail/.env`에서
`STATIC_PYTHON`, `STATIC_MODEL_PATH`로 지정할 수 있다. 기본 경로는 운영체제에 맞춰 선택한다.

```dotenv
# Mac 예시, 실행 위치 src/gmail 기준
STATIC_PYTHON=../detector/.venv/bin/python
STATIC_MODEL_PATH=../detector/models/prompt_injection.joblib
# Windows: STATIC_PYTHON=../detector/.venv/Scripts/python.exe
```

3. Docker Desktop과 도구 호출을 지원하는 Ollama 모델을 준비한다.
   [격리 이미지·Ollama 준비](dynamic-analysis.md)를 따른다.
4. 기존 Gmail 백엔드를 재시작하고 대시보드의 설정에서 Gmail을 연결한다.
5. **자동 분석 → Ollama 모델 선택 → 자동 분석 사용 → 설정 저장**을 한 번 수행한다.
   모델의 도구 지원은 저장 시 `/api/show`로 확인한다. 정적 준비 상태도 같은 화면에 표시된다.
6. **로컬 수집** 화면으로 이동한다. 수집된 메일의 정적 분류와 조건에 맞는 동적 분석이 자동 진행된다.

## 동작

```text
대시보드 메일 수집 (POST /api/mails + CSRF)
  → 계정·입력 전체 해시·정적 모델·분석 설정으로 중복 확인
  → 암호화된 정적 분석 대기열
  → 실제 prodog_sast 기존 ML + BERT-tiny Transformer 분류
  → 각 모델 자체 임계값으로 낸 판정 중 더 높은 위험 단계 선택
      ├ safe: 동적 분석 생략
      ├ suspicious / danger: Ollama 동적 분석 대기열
      └ 분류 실패: static_error (정상으로 바꾸지 않음)
  → 메일마다 새 격리 환경에서 1개씩 실행
  → 명령·stdout/stderr·파일 변경·고정 실험 목표 관찰 기록
```

정적 분류는 별도 작업자가 순차 처리한다. 긴 LLM 실험 중에도 다음 메일의 정적 분류는 진행된다.
두 분류기는 같은 메일을 독립적으로 평가하며 호출 순서는 기존 ML 다음 Transformer다.
동적 분석은 수동 실험과 같은 실행기를 사용하고, 전체에서 동시에 1개만 실행한다.
정적·동적 대기열은 각각 최대 100개이며 초과 시 오류를 표시한다. 조용히 정상 처리하지 않는다.

정적 입력은 탐지기의 `collect_api_to_model_text`를 그대로 사용해 제목·발신자·plain·HTML을 전달한다.
Transformer는 로컬 가중치만 읽고 모델 다운로드·외부 API를 호출하지 않는다. 파일 일부가 없거나
실행에 실패하면 정적 분석 실패로 표시한다. 기존 단일 ML 구성의 호환은 유지한다.
모델 식별자는 두 모델의 가중치·토크나이저·설정 전체를 반영하므로 모델 변경 시 이전 결과를 재사용하지 않는다.
메일 본문을 수집하지 못한 경우 분류하지 않는다. 일부만 수집한 메일은 기존 누락 경고를 유지한다.
동적 모델에는 일반적인 요약 과제와 원래 메일을 주며 정적 점수나 악성 정답 라벨을 알려주지 않는다.
동적 입력 한도 초과는 등록 실패로 남고 자동으로 본문을 잘라 실행하지 않는다.

## 결과 읽기

대시보드와 메일 상세에서 정적 판정과 자동 실행 상태를 확인한다.
각 정적 모델의 확률·임곗값은 화면에서 0~100점으로 변환해 표시한다.
두 모델의 확률은 직접 비교하지 않는다. 최종 판정은 `safe < suspicious < danger` 중 높은 단계다.
상단 점수는 그 단계를 결정한 모델의 대표 점수이며 보정된 결합 확률이 아니다.
모델별 점수·판정·임계값과 결정 모델(`decided_by`)을 상세 화면에서 확인한다.
동적 실행에 실패하거나 공격이 관찰되지 않아도 정적 위험 판정을 낮추지 않는다.
메일 상세의 실행 기록 링크에서 전체 명령·출력·파일 스냅샷을 확인한다.
긴 출력은 암호화 로그에 보관하고 모델은 `read_output`으로 추가 구간을 조회한다.
대화 범위가 조정될 수 있으므로 모델이 실제로 받은 내용은 `model_input` 로그로 확인한다.
페이지·문맥 정책과 출력 저장 한도는 [동적 분석 안내](dynamic-analysis.md)에 정리했다.

자동 상태는 `static_queued`, `static_running`, `static_error`, `skipped`,
`dynamic_queued`, `dynamic_running`, `completed`, `error`, `cancelled`이다.
`completed`는 대화 종료를 뜻한다. 메일의 안전성이나 요약 정확성을 보증하지 않는다.
가짜 토큰 유출 관찰은 `/workspace/leak.txt`에 실험용 토큰이 존재하는지를 확인하는 고정 목표다.
임의 공격의 자동 성공 판정은 아니다. 실제 공격 유형별 목표·정상 작업 성공률은 별도로 평가한다.

## 반복 실행·재시작·중지

- 같은 메일·내용·모델·설정의 완료 결과와 진행 중인 작업은 반복 수집해도 재실행하지 않는다.
- 설정을 바꾸거나 자동 분석을 껐다 켜면 새 설정 세대로 처리한다.
- 같은 세션에서 중지된 결과는 새로고침해도 다시 실행하지 않는다. 로그아웃 후 다시 연결하면
  취소된 작업은 새 시도로 진행할 수 있으며, 완료된 결과는 계속 재사용한다.
- 정적 환경을 고친 뒤에도 오류가 남아 있으면 자동 분석을 껐다 켜고 다시 수집한다.
- 재시작 시 아직 시작하지 않은 정적·동적 대기열을 복구한다. 실행 도중 끊긴 동적 작업은
  오류로 남기고 환경 제거를 시도한다. 해당 작업을 성공으로 처리하거나 자동 재실행하지 않는다.
- 전역 `EXPERIMENTS_ENABLED=false`이면 복구된 동적 작업도 실행하지 않는다.
- 자동 분석 해제·로그아웃·Gmail 재연결 필요 상태가 감지되면 해당 계정의 작업을 중지한다.
  다른 계정의 작업은 중지하지 않는다. 계정 연결 해제 시 실험 기록 파일을 추가로 삭제하지 않는다.
- GET 메일 조회·GET 상태 조회는 실행을 시작하지 않는다. 상태 폴링도 새 작업을 만들지 않는다.
- 메일 수집은 대시보드 진입·새로고침·더 불러오기로 수행한다.
  Gmail push 알림이나 화면을 닫은 동안의 주기적 수집은 구현 범위가 아니다.

## 데이터와 접근

자동 설정·분류 결과·대기 상태는 기존 로컬 SQLite의 계정별 테이블에 저장한다.
develop의 명시적 POST `/api/sync`는 기존 `DETECTOR_MODEL_PATH` 탐지와 Supabase 저장 계약을
유지하지만 동적 분석을 등록하지 않는다. `SUPABASE_USER_ID` 고정 테스트 사용자용 데모이며,
자동 분석 결과의 Supabase 저장이나 실제 로그인 사용자 연결을 구현한 것은 아니다.
정적 대기 중의 본문은 기존 암호화 키로 암호화하고 분석 완료/등록 후 임시 입력을 비운다.
새 동적 실행 기록 파일도 암호화한다. 계정별 실험 결과는 로그인한 계정에서만 조회할 수 있다.
이전 버전의 평문 수동 실험 파일은 읽기 호환만 유지하며 자동 변환하거나 삭제하지 않는다.
다운로드한 결과 JSON은 평문이다. 실제 메일이 포함될 수 있으므로 팀 공유 전 내용을 확인한다.
기존 Gmail 메타데이터 테이블에는 본문을 추가하지 않는다. API 키와 Gmail 토큰은 격리 환경에 넣지 않는다.

## 검증 범위

기본 테스트는 실제 메일·외부 추론을 사용하지 않는다.
환경 플래그를 켠 통합 테스트는 지정한 신뢰할 수 있는 모델로 실제 정적 ML을 실행하고
실제 Docker 안에서 명령을 실행한다. LLM 응답은 고정된 테스트 응답이다.
합성 테스트 모델은 연결 검증용이며 팀 모델·탐지 성능 평가를 대체하지 않는다.

```bash
PRODOG_DOCKER_TESTS=1 PRODOG_STATIC_ML_INTEGRATION=1 \
PRODOG_STATIC_TEST_PYTHON=/경로/탐지기/python \
PRODOG_STATIC_TEST_MODEL=/경로/신뢰하는/테스트모델.joblib \
uv run pytest tests/test_sandbox_live.py -q
```

실제 설치한 Qwen과 팀의 두 정적 모델을 함께 검증하는 선택적 테스트도 있다. 합성 메일과
별도 임시 DB를 사용하며 실제 Gmail 세션·자동 설정은 변경하지 않는다. 통과는 정확도·공격 성공률 평가가 아니다.

```bash
PRODOG_OLLAMA_TEST_MODEL=qwen3:4b-instruct uv run pytest tests/test_ollama_live.py -q -s
```
