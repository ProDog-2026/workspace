# ProDog 최종 판단 방식 비교 보고서

작성일: 2026-10-08  
상태: 설계·문헌 비교 완료, 동일 데이터 실측 비교 전

## 한눈에 보는 결론

ProDog는 Gmail 메일을 가져와 요약·정리하고, 메일 안에 AI를 속이려는 지시가 있으면 근거와 함께 알려주려는 프로젝트다. 현재 로컬 코드에는 **Gmail 읽기와 분석 입력 추출까지** 구현되어 있다. 탐지기, 요약기, Jev 최종 판단기는 아직 연결되지 않았다.

이번 비교의 질문은 **“여러 탐지 결과를 최종 경고로 바꿀 때, 직접 작성한 규칙보다 Jev가 도움이 되는가?”**다. 현재 근거로는 Jev 도입을 확정할 수 없다. 먼저 설명 가능한 규칙을 기준선으로 만들고, 같은 합성 메일에 Jev를 적용해 놓친 공격, 정상 메일 오경고, 판단 보류, 처리 시간과 외부 전송 범위를 비교한다.

## 비교 대상과 역할

| 방식 | 하는 일 | 장점 | 확인할 위험 |
| --- | --- | --- | --- |
| 코드 기반 판단 규칙 | 수집 경고, 정적 탐지 결과, 동적 탐지 결과를 명시한 조건으로 합친다 | 재현과 설명이 쉽고 모델 호출이 필요 없다 | 새로운 조합과 애매한 문맥을 놓칠 수 있다 |
| 공식 Jev | 메일 상태와 질문을 API에 보내 정해진 선택지의 확률을 받는다 | 구조화된 판단을 비교하기 좋다 | 외부 전송, API 의존성, 공격 문구의 판단 교란, 한국어 메일 성능 미확인 |
| 로컬 OpenJev 계열 | 공개 로컬 모델에서 선택지 확률을 얻는다 | 로컬 구성 시 본문을 외부 API에 보내지 않을 수 있다 | 공식 Jev와 다른 구현·가중치·확률 보정, 장비 자원과 품질 편차 |

**공식 Jev와 OpenJev는 같은 모델이 아니다.** OpenJev는 여러 공개 구현 중 하나를 택해야 하며, 프로젝트 이름만으로 품질이나 실행 방식이 정해지지 않는다. 비교 실험에서는 저장소·커밋·기반 모델·설정을 고정해 기록한다. 공식 Jev의 Choice·Score·Noul은 분류·점수화용 출력이며 메일 요약문 생성에 쓰는 모델은 아니다. 요약은 별도의 생성 모델 또는 로직으로 평가해야 한다.

## 이번 비교에서 특히 중요한 점

1. **탐지와 최종 판단은 다른 문제다.** Jev가 탐지기 결과를 잘 합치는지 보려면 모든 방식에 동일한 탐지기 결과를 넣어야 한다. 탐지기 자체를 바꾸면 차이의 원인을 알 수 없다.
2. **공격 메일을 그대로 판단 모델에 넣으면 모델도 공격 대상이 된다.** TypeSafe는 Jev 1.13이 적대적 입력에 흔들릴 수 있다고 명시한다. 메일 본문을 입력하는 실험과, 검증된 탐지 특징만 입력하는 실험을 분리한다.
3. **“형식이 맞는 답”은 “맞는 판정”이 아니다.** 높은 확률도 ProDog 메일에서의 정확도를 증명하지 않는다. 점수 기준은 별도 평가 자료로 정한다.
4. **읽기 전용 권한으로 실제 격리·차단은 할 수 없다.** 현재 Google 권한은 `gmail.readonly`다. 이 보고서의 출력은 사용자에게 보여주는 경고·검토 요청이지 Gmail 메일 이동이나 삭제가 아니다.
5. **수집이 불완전하면 안전으로 판단하지 않는다.** 첨부 내용 미분석, 잘린 메일, 파싱 오류는 판단 방식과 관계없이 별도 상태로 남긴다.

## 공정한 비교 실험

### 입력 자료

- 개인의 실제 Gmail 메일 대신 자체 제작하거나 사용 허가가 분명한 메일을 사용한다.
- 최소 40건으로 시작한다: 정상 20건, 프롬프트 인젝션 20건. 정상 사례에는 보안 교육 문구처럼 공격 키워드가 있어도 AI에게 명령하지 않는 사례를 포함한다.
- 공격은 HTML 숨김 문구, 역할 사칭, 다른 메일 검색·외부 전송 요구, 요약 결과 조작, 한국어·영어 변형으로 나눈다.
- 같은 원본의 변형은 한 묶음으로 다룬다. 일부 사례로 규칙·질문 문구를 조정하고 나머지 사례로 최종 평가한다. 최종 평가 사례를 보면서 임계값을 바꾸지 않는다.
- 각 사례에는 원본, 사람이 정한 정답, 공격 위치·목표, 수집 완전성, 정적·동적 탐지기의 **고정된 출력**을 기록한다. 공격 본문과 정답은 판단 모델에 한꺼번에 보내지 않는다.

### 세 방식에 공통으로 요구할 출력

```json
{
  "case_id": "synthetic-001",
  "decision": "no_flag | review | high_risk | incomplete | error",
  "reason_codes": ["html_hidden_instruction"],
  "elapsed_ms": 0
}
```

`no_flag`는 “이 비교에서 경고 신호를 찾지 못함”이지 안전 보증이 아니다. `incomplete`와 `error`를 정상 판정에 섞지 않는다. Jev의 확률과 confidence는 원본 응답을 별도 기록하되, 서로 다른 구현의 숫자를 같은 확률 품질로 간주하지 않는다. 원문 메일이나 개인정보를 결과 로그에 넣지 않는다.

### 보고할 수치

| 지표 | 계산·기록 방법 | 이유 |
| --- | --- | --- |
| 공격 탐지율 | 공격 사례 중 `review` 또는 `high_risk`로 표시한 비율 | 놓친 공격을 본다 |
| 정상 오경고율 | 정상 사례 중 `review` 또는 `high_risk`로 표시한 비율 | 쓸 수 없는 과다 경고를 본다 |
| 판정 가능 비율 | `incomplete`·`error`를 제외한 비율 | 실패를 숨기지 않는다 |
| 근거 일치 | 이유 코드가 실제 공격 위치·행동을 가리킨 사례 수 | 설명 가능한 경고인지 본다 |
| 처리 시간 | 같은 장비에서 메일 1건의 중앙값·95백분위 | 시연과 실제 사용 지연을 본다 |
| 비용·데이터 경계 | API 요청량·과금, 외부로 보낸 필드, 로컬 CPU/GPU·메모리 | 운영 가능성과 개인정보 영향을 본다 |

건수가 작은 초기 실험 결과는 일반적인 탐지 성능으로 확대하지 않는다. 결과표에는 건수 분자/분모와 실패 사례를 함께 쓴다.

## 현재 결과

| 확인한 사실 | 근거 |
| --- | --- |
| Gmail 연결·메일 목록·본문 조회는 로컬 코드와 실제 계정으로 검증했다 | [검증 기록](verification.md) |
| 본문·RAW는 로컬 DB에 저장하지 않고 메타데이터와 암호화 토큰을 저장한다 | [통합 문서](integration.md), `src/prodog_gmail/store.py` |
| Jev·OpenJev와 규칙 기준선의 ProDog 메일 비교 수치 | **아직 없음** |
| 메일 요약 품질과 공격 문구를 따라 하지 않는지에 대한 수치 | **아직 없음** |

현재 결정은 **규칙 기준선부터 구현하고 Jev는 보조 비교 대상으로 둔다**는 제안이다. Jev가 같은 사례에서 오경고를 줄이거나 놓친 공격을 발견하고, 그 이득이 외부 전송·지연·복잡도를 상쇄한다는 증거가 생기면 도입을 재검토한다.

| 방식 | 공격 탐지 (건/건) | 정상 오경고 (건/건) | 판정 불가 (건/건) | 지연 중앙값/95백분위 | 외부 전송 | 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| 코드 규칙 | 미측정 | 미측정 | 미측정 | 미측정 | 없음 | 보류 |
| 공식 Jev | 미측정 | 미측정 | 미측정 | 미측정 | 테스트 입력 전송 | 보류 |
| 로컬 OpenJev (선정 구현 명시) | 미측정 | 미측정 | 미측정 | 미측정 | 로컬 구성에 따라 없음 | 보류 |

각 오탐·미탐의 `case_id`와 원인을 표 아래에 적는다. 동일한 사례·입력·질문·버전으로 다시 실행할 수 있어야 한다.

## 포트폴리오에 넣을 이야기

“메일을 읽고 요약하는 AI가 외부 메일 속 지시를 명령으로 받아들이는 위험을 다뤘다. 내가 맡은 Gmail OAuth·메일 수집 모듈을 실제 계정으로 검증했고, 메일 원문은 저장하지 않으면서 분석에 필요한 입력과 수집 경고를 만들었다. 팀의 최종 판정 방식으로 단순 규칙과 Jev를 비교할 때는 같은 메일·같은 탐지 결과를 사용하고, 놓친 공격·정상 오경고·판정 실패·개인정보 전송을 함께 평가하도록 설계했다.” 실측 결과가 나오기 전에는 Jev가 성능을 개선했다고 쓰지 않는다.

## 출처와 범위

- [TypeSafe AI 빠른 시작](https://docs.typesafe.ai/introduction/quickstart): 공식 Jev API의 입력·출력과 Choice·Score·Noul
- [TypeSafe AI Jev 1.13 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13): 적대적 입력, 선택지 순서, 수치 판단, 긴 입력 등의 한계
- [TypeSafe AI confidence 설명](https://docs.typesafe.ai/confidence): 출력 확률과 confidence의 의미
- [OpenJev 공개 구현 예시](https://github.com/lookski/openjev): 공식 Jev와 다른 로컬 구현 방식 및 자체 한계. 이 저장소는 팀의 채택 구현으로 확정되지 않았다.
- [OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/): 외부 입력과 모델의 신뢰 경계

위 외부 문서는 구현·제품 설명의 출처이지 ProDog에서 성능을 측정했다는 근거가 아니다.
