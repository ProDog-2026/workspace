# ProDog 설계 검토

검토일: 2026-09-27. 기준은 현재 Vault의 `프로젝트-개요.md`와 이번 메일 연동 모듈이다.
아래 내용은 팀의 확정 결정을 대신하지 않는 구현자 의견이다.

## 읽기 연동과 차단 주장을 구분한다

현재 구조로 할 수 있는 일은 Gmail을 읽고 위험한 입력을 찾아 사용자에게 알리는 것이다.
Gemini나 Copilot의 메일 접근을 이 코드가 중개하지 않으므로, “AI가 읽기 전에 항상 차단한다”는 순서 보장은 없다.
`gmail.readonly`에는 메일 이동·삭제 권한도 없다.

초기 설명은 “Gmail에서 프롬프트 인젝션 의심 메일을 수집·분석하는 도구”로 좁히는 편이 정확하다.
차단 효과 시연은 팀이 제어하는 로컬 AI에 같은 메일을 넣고, 검사 전후에 어떤 도구 호출이 달라지는지 보여주면 된다.
실제 Copilot 제로데이 재현이나 제품 수준의 메일 차단을 구현했다고 설명하지 않는다.

## 수집 누락을 탐지 성공처럼 처리하지 않는다

첨부파일, 큰 메일, 깨진 MIME, 잘린 본문은 공격자가 이용할 수 있는 경계다.
이번 API는 `warnings`, `truncated`, `attachments`를 내보내며 첨부 내용은 분석하지 않는다.
후속 판단 로직에는 `위험`, `탐지 없음` 외에 `수집 불완전`과 `분석 실패` 상태가 필요하다.

성능표에는 정상/공격 건수뿐 아니라 수집 실패 건수와 분석 제외 건수도 남긴다.
실패한 샘플을 조용히 빼면 실제 사용 조건과 다른 숫자가 나온다.

## 정규화 전에 공격 증거를 지우지 않는다

화면을 안전하게 표시하는 일과 탐지용 입력을 만드는 일은 다르다.
HTML 태그·주석을 무조건 삭제하면 흰 글씨, 숨김 요소, 주석 속 명령이 사라질 수 있다.
이번 모듈은 plain과 HTML 원문을 메모리에서 보존하며 화면에는 텍스트로만 출력한다.

다음 분석 단계에서는 원문 보기와 정규화 보기를 함께 유지하고 변환 위치를 기록하는 것이 좋다.
탐지 구간이 어느 본문의 어느 위치인지 매핑할 수 있어야 팀원이 결과를 설명하고 오탐을 고칠 수 있다.
`UNTRUSTED` 필드 하나를 붙이는 것 자체가 모델의 지시 따르기를 막아주는 보안 장치는 아니다.
분석기의 도구 권한 제한, 외부 요청 차단, 구조화된 출력 검증도 별도로 필요하다.

## 모듈 경계를 먼저 합의한다

이번 WBS는 연결과 수집으로 닫는다.
다음 작업은 다음 입력·출력 계약을 팀원과 맞추는 것이다.

| 담당 단계 | 입력 | 출력 |
| --- | --- | --- |
| 수집 | 사용자에게 귀속된 Gmail 연결, 메일 ID | 원문 파싱 결과, 해시, 수집 경고 |
| 정적 분석 | 제목·발신자·plain·HTML·정규화 보기 | 규칙 ID, 위치, 점수, 처리 실패 |
| 동적 분석 | 신뢰할 수 없는 분석 입력, 제한된 실행 환경 | 구조화된 결과, 타임아웃·실패 |
| 판단 로직 | 두 분석 결과와 수집 완전성 | 판정, 근거, 판정 불가 사유 |
| 대시보드 | 사용자에게 귀속된 결과 | 상태·근거 표시와 재검사 |

연결 계정 ID와 Gmail message ID는 함께 다룬다.
서로 다른 사용자의 동일한 message ID를 같은 기록으로 합치면 안 된다.
탐지 구간에도 개인 정보가 들어갈 수 있으므로 본문을 저장하지 않는다는 원칙만으로 로그의 개인정보 문제가 끝나지는 않는다.

## 우선순위

1. 실제 동의·목록·본문·갱신은 2026-09-28 확인했다. 별도 시험 계정에서 만료 후 재연결·철회를 추가 검증한다.
2. API 입력 계약을 정적 분석·동적 분석·판단 담당자와 맞춘다.
3. 자체 합성 메일로 정상/공격/첨부/인코딩/불완전 수집 회귀 세트를 유지한다.
4. 팀 서비스에 붙일 때 Supabase 사용자 귀속과 RLS를 검증한다.
5. 그 뒤 지속 동기화, Pub/Sub, 첨부 분석 여부를 결정한다.

목록 조회는 현재 페이지의 각 메일 RAW를 받아 파싱한 뒤 메타데이터만 반환한다. 시연 규모에서는 동작하지만 팀 서비스에 통합할 때는 목록용 메타데이터 조회와 본문 분석 요청을 나누면 전송량과 응답 시간을 줄일 수 있다. 본문을 필요할 때만 읽는 쪽이 데이터 접근 범위도 더 명확하다.

공개 서비스 전환은 별도 범위다.
`gmail.readonly`는 restricted scope이며 Google의 검증 요구와 테스트용 예외를 함께 확인해야 한다.
학생용 로컬 데모에 곧바로 운영 서비스 비용이 필요하다고 단정하지 않는다.
[Gmail 권한 분류](https://developers.google.com/workspace/gmail/api/auth/scopes), [검증 예외](https://support.google.com/cloud/answer/13464323?hl=en)
